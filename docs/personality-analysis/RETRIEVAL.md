## 1. 🔴 발견 1 — 이어붙인 쿼리는 마지막 조건이 이긴다

`VECTORDB.md` §3의 `build_query()`는 조건들을 `", ".join()` 했습니다. 이게 틀렸습니다.

"두 편으로 분열"된 팀을 넣으면 조건이 4개 걸립니다:

```
쿼리: "팀이 두 편으로 갈라진 조합, 주도적인 구성원이 절반을 넘는 조합,
       결론부터 말하는 사람과 배경부터 말하는 사람이 섞인 조합, ..."

기대: TEAM_SPLIT   실제: COMMS_SPLIT   ❌
```

**원인은 임베딩이 아니라 산술입니다.** 문장을 이어붙이면 벡터가 조건들의 평균 쪽으로 끌려가고, 어휘가 가장 많은 조건이 그 평균을 지배합니다. 우선순위 정보는 join 하는 순간 사라집니다.

**고친 방식** — 조건별로 따로 검색하고 우선순위대로 합칩니다.

```python
def retrieve_for_team(chem, k=3):
    hits, seen = [], set()
    for prio, cond_id, qtext in build_query(chem):   # 우선순위 오름차순
        for cid, score in retrieve(qtext, k=2):      # 조건 하나 = 검색 한 번
            if cid in seen: continue
            seen.add(cid); hits.append(...); break
    return hits[:k]
```

**부수 효과가 하나 더 있습니다.** 마찰 2개가 우선순위대로 나오므로, 화면에 무엇을 먼저 보일지가 자동으로 정해집니다. 별도 정렬 로직이 필요 없습니다.

## 2. 🔴 발견 2 — 유형 16개는 벡터 인덱스에 넣지 않는다

처음엔 `TYPES16.md` §5대로 16유형을 인덱싱했습니다. 재현 시험:

```
원문 그대로 질의       → 오답 0/16   ← 질의=문서라 자명한 시험. 근거로 못 씀
바꿔 쓴 문장으로 질의  → 오답 2/6    ← 이게 실제 상황
     "일정을 먼저 짜두고 각은 안 세우되 말은 짧게 끝낸다"   → ALHD (정답 PLHD)
     "일정을 먼저 짜두고 부드럽게 배경부터 풀어서 설명한다"  → ALHD (정답 PLHI)
```

**그런데 이건 문단을 고칠 문제가 아니라 설계 문제였습니다.**

유형 코드는 `compute_chemistry`가 **결정론으로 계산해냅니다**. 정확한 키가 이미 손에 있는데 왜 검색으로 찾습니까. 딕셔너리 조회로 바꾸니 8/8, 언제나 100%입니다.

**가르는 기준 한 줄:**

> **정확한 키가 있으면 조회, 없으면 검색.**
> 유형은 키가 16개로 유한하다 → 조회. 팀 패턴은 조건 조합이 무한하다 → 검색.

인덱스에 들어가는 것: **팀 패턴 11 + 논문 초록 10.** 유형 16은 코드 안 딕셔너리입니다.

> 발표 문장: *"검색을 쓸 곳과 안 쓸 곳을 테스트로 갈랐습니다."*
> 이건 "벡터 DB를 썼다"보다 강한 문장입니다. 안 쓴 이유를 댈 수 있는 팀이 드뭅니다.

## 3. 🔴 발견 3 — 유사도 1등을 헤드라인으로 쓰면 안 된다

발견 1을 고친 뒤에도 2건이 틀렸습니다. 이번엔 우선순위 배정이 문제였습니다.

`faultline.diagnose()`의 **"부분적으로 갈린 조합"은 `else` 분기**입니다. 앞의 조건에 안 걸린 팀이 전부 여기로 떨어집니다 — `chemistry.py`의 검증 케이스 6개 중 4개가 이 진단을 받습니다. **거의 모든 팀에 뜨는 진단은 정보량이 0에 가깝습니다.** 그런데 문단이 길어서 유사도는 높게 나옵니다.

실제로 유사도만으로 1등을 뽑으면 이렇게 됩니다:

| 팀 | 유사도 1등 | 나와야 할 것 |
|---|---|---|
| 두 편으로 완전 분열 | COMMS_SPLIT (0.471) | **TEAM_SPLIT** (0.270) |
| 전원 캡틴 | TEAM_PARTIAL (0.293) | **DRIVE_ALL** (0.219) |
| 계획 한쪽 몰림 | TEAM_ONE_AXIS (0.385) | **PLAN_ONESIDED** (0.256) |

**정답이 전부 유사도에서 지고 있습니다.** 검색 품질이 나빠서가 아니라, 유사도가 답할 수 있는 질문이 아니기 때문입니다.

**우선순위 기준 = 등급을 실제로 바꾸는 순서.** 이건 자의적 순서가 아니라 `compute_chemistry` 코드에서 그대로 읽어낸 것입니다.

| p | 케이스 | 근거 |
|---|---|---|
| 0 | TEAM_SPLIT · TEAM_ISOLATED | `total`에 0.75 / 0.85를 곱한다 = 등급 강등 |
| 1 | DRIVE_NONE | `drive_zero` 게이트 → 등급 C 강제 |
| 2 | DRIVE_ALL · DRIVE_EXCESS | 축 점수를 0.5 아래로 떨어뜨린다 |
| 4·5·6 | COMMS_SPLIT · CONFLICT_SPLIT · PLAN_ONESIDED | 축 가중치 순 (.25 / .20 / .20) |
| 7·8 | TEAM_PARTIAL · TEAM_ONE_AXIS | **등급을 안 바꾼다.** 맥락이지 헤드라인이 아니다 |
| 9 | TEAM_MIXED | 다른 조건이 하나도 안 걸릴 때만 |

> 심사위원 질문 대비: *"검색 결과 순서는 누가 정하나요?"* → **"유사도가 아니라 등급에 미치는 영향 순입니다. 그 순서는 채점 코드에서 그대로 나옵니다."**

## 3.5 🔴 발견 4 — 팀 패턴에서 검색은 아는 답을 확인할 뿐입니다

**§0의 6/6은 검색 품질의 증거가 아닙니다.** 자명성 검사를 돌려보면 드러납니다.

```
A. 조건 문장으로 자기 자신 찾기        11/11   ← 조건 문장 = 케이스의 query 필드다. 자명하다
B. 바꿔 쓴 조건 문장으로 찾기          11/11   ← 검색이 실제로 하는 일. 2등과 2~3배 차이
C. build_query() 반환값               (priority, case_id, query_text)
                                       ↑ case_id가 이미 들어 있다
```

**`build_query()`는 trigger 조건에서 케이스 id를 이미 결정론으로 뽑아냅니다.** 조건 → 케이스가 1:1이고, 조건은 `compute_chemistry`의 축 점수에서 나옵니다. 그다음 `retrieve()`가 문장을 임베딩해서 찾는 건 **이미 손에 쥔 답을 확인하는 것**입니다.

이건 발견 2와 정확히 같은 논리입니다 — **정확한 키가 있으면 조회, 없으면 검색.** 유형 16에 적용한 기준을 팀 패턴 11에도 적용하면 답이 같습니다.

### 그러면 벡터 DB의 진짜 자리는 어디인가

**논문 초록 인덱스입니다.** 여기엔 정확한 키가 없습니다 — 케이스 하나에 어떤 논문이 붙을지는 규칙으로 못 씁니다(1:다, 조합 무한). `evidence` 인덱스는 검색이 맞습니다.

| | 무엇 | 방식 | 이유 |
|---|---|---|---|
| 유형 16 | 개인 유형 카드 | **조회** | 코드가 정확한 키를 계산해낸다 |
| 팀 패턴 11 | 조건 → 케이스 | **조회** | trigger가 1:1로 결정한다 |
| 논문 초록 10 | 케이스 → 근거 | **검색** | 정확한 키가 없다. 여기가 벡터 DB 자리 |

`search_test.py`의 팀 패턴 검색은 **회귀 테스트로 남깁니다** — 케이스 문단이 서로 구별되는지 재는 용도로는 여전히 유효합니다. 런타임 경로만 조회로 내립니다.

> 발표 문장이 더 세집니다: *"세 군데 중 두 군데는 검색을 뺐습니다. 남긴 한 군데만 벡터 DB가 실제로 일을 합니다."*

## 4. 케이스가 10건이 아니라 11건입니다

`VECTORDB.md`가 잡은 구성은 *진단 5 + 주도성 3 + 소통 갈림 + 계획 한쪽 = 10*이었습니다.
**`CONFLICT_SPLIT`이 빠져 있었습니다** — `chemistry.py`의 `score_conflict()`가 마찰을 내는데 대응 케이스가 없었습니다. 그대로 뒀으면 갈등 축이 갈린 팀에서 엉뚱한 케이스가 검색됐을 겁니다.

**11건 = 진단 5 + 주도성 3 + 소통 + 갈등 + 계획.**

## 5. 이 코드가 그대로 폴백입니다

## 8. 임베딩 모델 — 논문이 아니라 제약과 우리 테스트로 정합니다

**순서가 중요합니다. 제약이 후보를 줄이고, 우리 테스트가 고릅니다. 논문은 각주입니다.**

### 왜 논문 서베이가 답을 못 주는가

1. **논문이 추천하는 1등을 우리가 못 씁니다.** 한국어 검색 특화 임베딩의 최신 연구는 KURE(고려대) 같은 오픈 모델을 가리키는데, Bedrock에 없습니다. 자가 호스팅하면 AWS 10점에 안 붙고 Day1 관문이 하나 늘어납니다.
2. **실제 후보가 2~3개뿐입니다.** Bedrock 모델 액세스가 열리는 임베딩 모델로 한정되면 서베이의 값어치가 거의 없습니다.
3. **코퍼스가 21건입니다**(팀 패턴 11 + 논문 초록 10). MTEB류 벤치마크는 수만 문서 기준이고, 21건에서의 순위와 상관이 약합니다. **AWS 문서 자체가 "고객이 직접 테스트하라"고 권고합니다** — 비영어 텍스트면 특히.
4. **우리는 이미 채점기를 갖고 있습니다.** `search_test.py`의 `retrieve()`를 후보 모델로 바꿔 끼우면 같은 시험을 보게 할 수 있습니다. 30분입니다. **우리 데이터에서 잰 숫자가 남의 벤치마크보다 강합니다.**

### 쓸 수는 있습니다

| | |
|---|---|

> 케이스 11건 규모에서 임베딩 모델의 우열은 나타나지 않습니다. **21건짜리 코퍼스는 임베딩이 이기는 판이 아닙니다.**

### 진짜 문제는 임베딩이 아니었습니다

자유 서술에서 **둘 다 2/7**입니다. 원인을 갈라보려고 케이스마다 '현장 발화' 두 줄을 덧붙이고 다시 쟀습니다:

| | 현행 | + 현장 발화 |
|---|---|---|
| TF-IDF | 2/7 | **4/7** |
| KURE-v1 | 2/7 | **2/7** |

**모델을 바꿔도 안 움직이고 어휘를 바꾸니 움직였습니다.** 케이스 문단은 분석가 어휘(*"조합" "구성원" "성향"*)로 쓰였고, 사용자는 구어체 불평(*"총대를 안 메요" "문서만 쌓여요"*)으로 칩니다. 검색기 품질 문제가 아니라 어휘 간극입니다.

그리고 4/7도 데모에 못 씁니다.

### 🔴 정정 — 자유 서술 입력은 넣지 않습니다

위 자유 서술 측정은 **기능 제안의 근거가 아니라 기각의 근거**입니다.

이 문서 이전 판은 "자유 서술 경로는 LLM 분류로 간다"고 적었습니다. **그 전제가 틀렸습니다.**

**우리 제품에 자유 서술 입력이 없습니다.** 입력은 8문항 선택형이고, 응답은 축 4개 이진값이 되며, 사람 사이의 가깝고 멂은 `compute_chemistry`가 **축 벡터로 계산**합니다. 텍스트 유사도가 개입할 자리가 원래 없습니다.

자유 서술을 넣자는 말이 나온 이유는 하나뿐이었습니다 — **벡터 검색에 일거리를 만들어주려고.** 그건 순서가 거꾸로입니다. 도구를 정당화하려고 입력 화면을 늘리는 건 STEP1 Over-engineering 그 자체이고, 화면 하나·검증 하나·실패 모드 하나가 Day1에 늘어납니다.

> **버리는 근거:** 요청받은 것("벡터 DB를 쓴다") ≠ 풀어야 할 것. 도구가 할 일이 없으면 일을 만들어주는 게 아니라 도구를 줄인다.

### 결론

**Titan Text Embeddings V2로 가고, KURE는 안 씁니다.** 벡터 DB는 §3.5대로 **논문 초록 인덱스 전담**입니다.

### 🟡 그런데 그 하나도 지금 규모에선 약합니다 — 조건이 붙습니다

정직하게 적습니다. 검색이 네 자리 중 세 자리에서 빠졌고, 남은 한 자리도 **초록 10편에서는 검색이 손매핑보다 낫다고 주장할 수 없습니다.** 케이스 11 × 논문 10이면 사람이 표 한 장으로 매핑할 수 있고, 그게 더 정확하고 검증도 됩니다.

**검색이 정당해지는 지점은 초록 30편입니다.** 11 × 30 = 330쌍이면 손매핑이 무너지고, 케이스를 추가할 때마다 다시 매핑해야 하는 문제도 생깁니다. 거기서부터 검색이 유일한 방법이 됩니다.

| 초록 편수 | 근거 연결 방식 | 이유 |
|---|---|---|
| 10편 (오늘 밤) | 벡터 검색 — **단, 손매핑 표를 정답으로 놓고 대조** | 이 규모에선 검색이 이겼다고 말할 수 없다 |
| **30편 (Day2)** | **벡터 검색** | 330쌍. 손매핑이 무너지는 지점 |

> **오늘 밤 할 일이 하나 정해집니다** — 초록 10편을 넣고 `케이스 → 논문` 손매핑 표를 같이 만드세요. 그 표가 검색의 채점기가 됩니다(§0 표와 같은 방식). Day2에 30편으로 늘렸을 때 정확도가 유지되는지 그 표로 잽니다.
>
> 심사위원 질문 대비: *"10건짜리에 벡터 DB가 필요한가요?"*
> → **"10편에서는 필요 없습니다. 저희는 손매핑 표를 정답으로 두고 대조했고, 30편에서 손매핑이 무너지는 걸 확인하고 검색으로 갔습니다."**

> 발표 문장: *"한국어 특화 임베딩 모델까지 실제로 붙여서 재봤습니다. 저희 데이터에선 더 낮았고, 원인은 모델이 아니라 코퍼스 어휘였습니다."*
> 논문을 인용한 것보다 강합니다. **안 쓴 이유를 숫자로 댈 수 있는 팀이 드뭅니다.**

### 정직한 갭

- **평가 문장을 제가 썼습니다.** 현장 발화와 자유 서술 쿼리 모두 자작이라 저작 편향이 있고, **n=7은 통계적 근거가 못 됩니다.** 방향만 읽으세요.

## 11. 24문항의 정보를 살립니다 — 단, 벡터 유사도로는 아닙니다

`[검증됨 · 2026-08-27 실측]` 스크립트: `continuous_test.py` · 구현: `chemistry_v2.py`

팀 제기: *"유형은 16개지만 문항은 24개다. 개인 간 조합도 팀 전체 조합도 다른데, 그걸 유사도로 봐야 하지 않나?"* — **앞부분은 맞고, 뒷부분은 아닙니다.**

### ✅ 정보 손실은 실재합니다

현행은 축당 6문항의 `4:2 / 5:1 / 6:0`을 **전부 `1`로 뭉갭니다.** 응답 분포만 다르고 나머지가 같은 두 팀을 넣어봤습니다.

| 팀 | 이진 소통값 | 소통 점수 | 등급 | 총점 | **실제 응답 격차** |
|---|---|---|---|---|---|
| 6:0 D ×3 vs 6:0 I ×2 | `[1,1,1,0,0]` | 0.40 | B | 0.468 | **1.00** |
| 4:2 D ×3 vs 4:2 I ×2 | `[1,1,1,0,0]` | 0.40 | B | 0.468 | **0.33** |

**격차가 3배인데 점수가 소수점까지 같습니다.** 24문항으로 늘린 값어치가 여기서 증발합니다.

연속 비율로 바꾸면 소통 **0.40 vs 0.80**, 총점 **0.54 vs 0.64**로 갈립니다.

### ❌ 그런데 벡터 유사도는 답이 아닙니다

`chemistry.py`의 검증 케이스 6개를 우리 규칙과 코사인 유사도로 각각 줄 세웠습니다.

```
등급 순위(우리): 이상적 > 소통 반반 > 한 명 겉돎 > 전원 캡틴 > 캡틴 0명 > 두 편 분열
유사도 순위    : 전원 캡틴 > 캡틴 0명 > 이상적 > 소통 반반 > 한 명 겉돎 > 두 편 분열
```

**유사도 1위가 '전원 캡틴'(등급 B)이고 2위가 '캡틴 0명'(등급 C)입니다.** 우리 1위 '이상적'은 3위로 밀립니다.

이유는 하나입니다 — **코사인은 모든 축을 "닮을수록 좋다"로 취급합니다.** 우리 핵심 IP는 그 반대입니다: 계획성은 **달라야** 좋고, 주도성은 **비선형**(0명도 전원도 나쁨), 갈등·소통만 같아야 좋습니다. **축마다 방향이 다른 걸 하나의 유사도 숫자로 표현할 방법이 없습니다.** 유사도로 바꾸는 순간 우리를 MBTI 궁합 앱과 구별해주던 게 사라집니다.

그리고 벡터 DB는 **많은 후보 중 가까운 걸 빨리 찾는** 도구입니다. 우리는 최대 10명, 45쌍이라 전수 계산이 즉시 끝납니다. 인덱스가 할 일이 없습니다.

### 채택안 — `chemistry_v2.py`

| | |
|---|---|
| 입력 | `confidence`(`"5:1"`)를 비율 0~1로 변환. **`SURVEY24.md` §9가 이미 계약에 넣어둔 필드입니다** |
| 축 점수 | 방향·가중치·등급 경계·게이트·faultline **전부 그대로**. 값만 연속 |
| 쌍 단위 궁합 | `pair_fit()` 추가 — 축별 방향을 적용한 가중 합 (근거: Andrés et al. 2011 쌍 단위 지수) |
| 호환성 | `confidence`가 없으면 1.0 / 0.0 / 0.5로 떨어짐 → **현행과 동일한 값** |
| **회귀 테스트** | `chemistry.py` 검증 케이스 6개에서 등급·총점·축점수·게이트 **6/6 완전 일치** |

**새 모델이 아니라 같은 규칙을 연속값 위에서 돌린 것입니다.** 그래서 되돌리기가 공짜입니다 — `confidence`를 안 넘기면 현행으로 돌아갑니다.

> 심사위원 질문 대비: *"문항을 24개나 받아서 4비트로 줄이는 거 아닌가요?"*
> → **"아닙니다. 6문항 중 몇 대 몇인지가 그대로 점수에 들어갑니다. 4:2인 팀과 6:0인 팀은 다른 점수를 받습니다."**

**미확인**: 등급 경계 0.70 / 0.45는 이진 분포 기준으로 잡은 값입니다. 연속으로 가면 총점 분포가 달라지므로 **실제 응답 20건으로 분포를 보고 경계를 다시 잡아야 합니다** `[미확인]`. 그전까지는 v1(이진)을 데모 정본으로 두고 v2를 나란히 돌려 비교하세요.
