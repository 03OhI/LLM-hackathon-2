## 1. 인코딩 — 여기가 전부입니다

축마다 유사/보완 방향이 달라 그냥 넣으면 순위가 뒤집힙니다(ρ = −0.075). **저장할 때만 보완축 부호를 뒤집습니다.**

```
저장:  b̃ = ( −(b_plan−½), −(b_drive−½), +(b_conf−½), +(b_comms−½) ) × √w
질의:  a  = (  (a_plan−½),  (a_drive−½),  (a_conf−½),  (a_comms−½) ) × √w
```

```
PLCD  저장 [-0.224, -0.296, 0.224, 0.250]
      질의 [ 0.224,  0.296, 0.224, 0.250]     ← 같은 사람인데 벡터가 다르다
```

> 🔴 **비대칭 인코딩입니다.** 저장은 `store_vector()`, 검색은 `query_vector()`. 바꿔 쓰면 에러 없이 조용히 틀립니다. 이게 이 코드의 유일한 함정입니다.

차원은 **4**입니다(S3 Vectors 한도 1~4096). 임베딩 모델이 필요 없습니다.

## 2. 인덱스 2개 — 함정을 분리해서 밟습니다

| 인덱스 | 차원 | 무엇 | 임베딩 모델 |
|---|---|---|---|
| `team-types` | 4 | 16유형 축 벡터 | **불필요** |
| `cases` | 1024 | 팀 패턴 11건 문단 | Titan Text Embeddings V2 필요 |

**`team-types`를 먼저 올려서 관문 8을 통과하세요.** 임베딩 모델 액세스는 별도 함정이라(`VECTORDB.md` §1), 리전·IAM 문제와 섞이면 원인 분리가 안 됩니다. 하나씩 밟는 게 빠릅니다.

## 3. 실행 순서

```bash
python upload_s3vectors.py --dry-run                 # AWS 없이 리허설. 지금 바로 됨
python upload_s3vectors.py --check                   # 리전 가용성만 확인
python upload_s3vectors.py --types                   # 관문 8 통과 (임베딩 불필요)
python upload_s3vectors.py --cases                   # 임베딩 액세스 열린 뒤
python upload_s3vectors.py --types --region us-east-1  # 서울에서 안 되면
```

### 실패하면 뜨는 메시지

| 증상 | 스크립트가 알려주는 것 |
|---|---|
| `UnknownServiceError` | boto3가 낡았습니다 → `pip install -U boto3` |
| `EndpointConnectionError` | 그 리전에 S3 Vectors가 없습니다 → `--region us-east-1` 또는 LocalStore 폴백 |
| `AccessDenied` | IAM에 `s3vectors:*` 없음 |
| 임베딩 `AccessDeniedException` | **Bedrock 콘솔 → Model access 에서 임베딩 모델을 따로 여세요.** 생성 모델이 열렸다고 임베딩까지 열린 게 아닙니다 |

## 4. 붙이자마자 반드시 할 것 — 로컬 대조

`verify_against_local()`이 원격 인덱스와 `LocalStore`의 순위를 16개 질의로 대조합니다. `upload_types()`가 자동으로 돌립니다.

**왜 필요한가:** `QueryVectors`는 similarity가 아니라 **distance**를 돌려주는데, **AWS 문서에 코사인 distance의 정의가 없습니다** `[미확인]`. 코드는 관례대로 `similarity = 1 − distance`로 되돌립니다. 정의가 다르면 값은 틀려도 **순위는 보존**되므로, 로컬 대조가 통과하면 안전합니다.

## 5. 청킹 — 안 합니다

**청킹은 긴 문서를 검색 단위로 쪼개는 작업**입니다. 우리 코퍼스 21건은 **처음부터 검색 단위로 쓴 글**이라 쪼갤 게 없습니다.

| 무엇 | 길이 | 처리 |
|---|---|---|
| 팀 패턴 케이스 11 | 230~270자 완결 문단 | **1 케이스 = 1 벡터** |
| 유형 카드 16 | — | 인덱스에 안 넣음 (§2) |
| 논문 초록 10 | 150~300 단어 | **1 논문 = 1 벡터** |

Titan V2 컨텍스트가 **8K 토큰**이라 초록은 절대 안 넘칩니다. 자를 이유가 물리적으로 없습니다.

### 실습 코드의 `RecursiveCharacterTextSplitter(500, 50)`을 쓰면 안 되는 이유 3개

1. **문서 경계를 무시합니다** — 두 케이스가 한 청크에 섞일 수 있습니다.
2. **메타데이터가 안 붙습니다** — `pattern_id`·`priority`·`action`이 청크 단위로 따라가지 않습니다. 우리는 우선순위 병합에 그게 필요합니다(`RETRIEVAL.md` §3).
3. **화면이 깨집니다** — `"먼저 할 일 —"` 줄만 따로 검색돼서 맥락 없이 뜹니다.

> **원칙 한 줄: 청크 = 검색 단위 = 화면에 보일 단위.**
> 이걸 어기면 검색은 맞는데 화면이 이상해지고, 원인을 찾기 어렵습니다.

### 논문 초록 넣는 규칙 (`papers.py`)

```
임베딩에 들어가는 것 : title + abstract           ← 사람이 읽을 문장
메타데이터로 가는 것  : 저자·연도·저널·축·효과크기   ← 화면에 띄울 값, 검색 대상 아님
```

- **초록은 원문에서 복사해 붙입니다.** 기억으로 쓰지 않습니다.
- `finding`(k·효과크기)은 원문을 열어야만 채웁니다. **`status == "verified"` 이고 `finding` 이 있어야만 화면에 출처가 뜹니다**(`displayable()`).
- 초록이 유난히 길면 자동 분할 대신 **결과 문단만 사람이 발췌**합니다. 10편 규모에선 그게 더 정확합니다.

`CASE_PAPER_MAP`이 **손매핑 표**이자 검색의 채점기입니다. 10편에선 손매핑이 검색보다 정확하고, 30편이 되면 무너집니다 — 그때 검색이 정당해집니다(§0 결론과 같은 논리).

## 6. 정직한 갭

- **실제 AWS 호출은 아직 안 했습니다.** `mock_s3_test.py`는 boto3 서비스 모델로 **파라미터 모양만** 검증합니다. 서버 동작·권한·요금은 검증 대상이 아닙니다.
- 코사인 distance 정의 `[미확인]` → §4 대조가 그걸 대신합니다.
- 서울 리전 S3 Vectors 지원 여부 `[미확인]` — `--check`가 첫 답을 줍니다.
- **이 인덱스가 지금 꼭 필요하지는 않습니다.** 5명이면 쌍이 10개라 전수 계산이 마이크로초입니다. 이건 *"된다"를 보이는* 코드지 *"필요하다"를 보이는* 코드가 아닙니다. 발표에서 그렇게 말하세요.
- **진짜 값어치는 `cases`와 논문 인덱스입니다.** 같은 `VectorStore` 인터페이스를 쓰므로 코드는 그대로 재사용됩니다.
