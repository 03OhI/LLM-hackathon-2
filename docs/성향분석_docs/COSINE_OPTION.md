## 0. BLUF — 회의에서 이 세 줄만 있으면 됩니다

1. **순수 코사인은 안 됩니다.** 우리 점수와 순위 상관 **ρ = −0.075**, 사실상 무관합니다.
2. **부호와 가중치를 넣은 코사인은 우리 쌍 점수와 순서가 완전히 같습니다.** 136쌍 전수에서 **1:1 단조 대응** — 우리 점수가 같은데 코사인이 갈리는 쌍 0건, 그 반대도 0건. 표현만 다릅니다.
3. **단 팀 수준은 원리적으로 안 됩니다.** 반례가 둘입니다 — '전원 캡틴'과 '캡틴 0명'이 **똑같은 값(−0.071)**, 그리고 안 B가 **소수점 4자리까지 같은데 등급이 A와 B로 갈리는 팀 쌍이 표본 4,000개 중 37건.** 튜닝으로 못 고칩니다.

**⇒ 결론: 팀 안은 틀리지 않았습니다. 다만 제대로 만들면 지금 코드와 같아집니다.**

## 1. 세 가지 안

| | 무엇 | 쌍 ρ | 팀 ρ |
|---|---|---|---|
| **안 A** | 순수 코사인 — 축 벡터 그대로 | **−0.075** | +0.143 |
| **안 B** | **계량 코사인** — 축별 부호·가중치 반영 | **+1.000** | +0.812 |
| **안 C** | 안 B + 주도성 비선형·게이트·faultline을 따로 붙임 | +1.000 | (현행과 동일) |

### 안 B의 수식

$$\text{sim}(a,b)=\frac{(a-c)^{\mathsf T} D\,(b-c)}{\lVert a-c\rVert\,\lVert b-c\rVert},\qquad D=\mathrm{diag}(d_k w_k)$$

- $c = 0.5$ (0~1 척도의 중점)
- $d_k = -1$ **보완축**(계획성·주도성 — 벌어질수록 좋다) / $d_k = +1$ **유사축**(갈등·소통)
- $w_k$ = 기존 가중치 (.20 / .35 / .20 / .25)

**부호가 핵심입니다.** $(a-c)(b-c)$는 두 사람이 같은 쪽일 때 양수인데, 보완축에서는 그게 나쁜 것이므로 계수를 뒤집습니다. 이걸 안 하면 안 A가 되고, 그래서 ρ가 −0.075로 무너집니다.

> 이게 제가 앞서 "코사인은 축별 방향을 못 담는다"고 한 것에 대한 **정정**입니다. **계량행렬 $D$를 넣으면 담깁니다.** 못 담는 건 그다음, 팀 수준입니다.

## 2. 🔴 팀 수준에서 깨지는 지점 — 이건 튜닝 문제가 아닙니다

**구성원이 전원 동일한 두 팀**으로 봅니다 — `(P,L,C,D)×5` 와 `(P,S,C,D)×5`.

```
              우리 규칙                        안 A      안 B
전원 캡틴   주도 0.25 · 등급 B · 총점 0.618   +1.000   −0.071
캡틴 0명    주도 0.00 · 등급 C · 총점 0.530   +1.000   −0.071
```

> ⚠️ 초판에서 이 표에 **§4(검증 케이스)의 숫자 0.637 / −0.043을 잘못 옮겼습니다.** §4는 구성원이 서로 다른 팀이라 값이 다릅니다. 위가 맞습니다.

두 팀 모두 **구성원이 전원 동일**합니다. 그래서 어떤 쌍 유사도로 봐도 모든 쌍이 같고, 평균도 같습니다. 안 A는 둘 다 +1.000, 안 B는 둘 다 −0.071입니다.

그런데 우리 규칙은 **캡틴 0명을 더 나쁘게** 봅니다 — 아무도 안 정하는 팀은 다른 게 좋아도 안 굴러가니까요(`drive_zero` 게이트 → 등급 C 강제).

**"몇 명이 주도하는가"는 집합의 성질이지 쌍의 성질이 아닙니다.** 쌍 유사도를 어떻게 평균 내도 나올 수 없습니다. 이건 가중치를 바꿔서 고쳐지는 게 아니라 **표현할 수 없는 것**입니다.

### 반례 ② 최솟값 게이트 — 이것도 확인됐습니다

4,000팀 표본에서 **안 B 값이 정확히 같은데 우리 등급이 갈리는 팀 쌍 37건**을 찾았습니다. 가장 선명한 한 쌍:

| 팀 | 안 B | 우리 등급 | 총점 | 축 점수 (계획·주도·갈등·소통) | 게이트 |
|---|---|---|---|---|---|
| PSCD·PSHD·ALHD·ASHD·ASHD | **+0.1857** | **A** | 0.920 | 1.00 · 1.00 · 0.60 · 1.00 | 없음 |
| PLCI·PLCI·ALCD·ASCD·ASCD | **+0.1857** | **B** | 0.493 | 1.00 · 0.45 · 1.00 · **0.40** | `axis_below_half` |

안 B 값이 **소수점 4자리까지 같은데 등급은 A와 B로 갈립니다.** 한 팀은 네 축이 고르고, 다른 팀은 소통 축만 0.40으로 무너졌습니다.

**코사인은 축을 하나의 스칼라로 합치므로 "어느 축이 무너졌는가"를 표현할 수 없습니다.** Halfhill et al.(2005)의 *"평균은 낮은 값을 가려버린다"*가 그대로 나타납니다. 게이트는 축 점수를 따로 계산해서 붙여야 하고, 그게 지금 코드입니다.

## 3. 벡터 DB에 실제로 올릴 수 있는가 — 됩니다, 근사로

$D$에 음수가 섞여 있어 $D = M^{\mathsf T}M$ 분해가 불가능합니다(양의 준정부호가 아님). **그래서 그대로는 표준 코사인 인덱스로 못 돌립니다.**

우회로가 있습니다 — **저장할 때 보완축 부호를 뒤집습니다.**

```
저장:  b̃ = ( −(b_plan−c),  −(b_drive−c),  +(b_conf−c),  +(b_comms−c) ) × √w
질의:  a  = (  (a_plan−c),   (a_drive−c),   (a_conf−c),   (a_comms−c) ) × √w
        → 표준 코사인 인덱스에서 그대로 검색된다
```

| 검증 | Spearman ρ |
|---|---|
| 저장-반전 코사인 vs 계량 코사인 | **+0.996** |
| 저장-반전 코사인 vs **우리 쌍 점수** | **+1.000** |

**순위가 완전히 보존됩니다.** (초판의 0.937 / 0.919는 위 가중치 버그 때문이었습니다.)

> ρ이 0.996과 1.000으로 갈리는 건 **동점 처리의 부동소수점 민감성**입니다. 계량 코사인은 float 값이 16가지로 보이지만 12자리로 반올림하면 12가지가 되어 우리 쌍 점수(12가지)와 **정확히 대응**합니다. 우리 점수가 같은데 코사인이 갈리는 쌍 **0건**, 그 반대도 **0건**입니다. 실행 환경에 따라 0.996 / 1.000이 오갈 수 있으니 **둘 다 "완전 일치"로 읽으세요.**

그리고 실용적으로 — **5명이면 쌍이 10개, 10명이면 45개**입니다. 인덱스가 할 일이 없습니다.

## 4. 그래서 코사인으로 가면 실제로 어떻게 되나

```
설문 24문항 → 축 4개
   ↓
[코사인]  쌍 점수 10~45개                ← pair_fit()을 대체. 그런데 ρ=1.000으로 같은 순서
   ↓
[기존 코드] 주도성 비선형 · faultline · 게이트 · 등급   ← 코사인이 못 하므로 그대로 남는다
   ↓
출력
```

**코사인이 대체하는 건 `pair_fit()` 함수 하나이고, 그것도 같은 순서를 냅니다.** 나머지는 전부 지금 코드가 그대로 합니다.

| | 바꾸면 얻는 것 | 잃는 것 |
|---|---|---|
| 안 B로 교체 | 표현이 "벡터 유사도"가 되어 설명이 짧아짐 | 쌍 점수 해상도 소폭 하락(정규화 때문에 극단값이 눌림) |
| 안 A로 교체 | — | 순위가 무너짐 (ρ=−0.075). **절대 안 됨** |
| 안 C | 없음 (안 B + 현행) | 코드가 두 갈래가 되어 유지비만 늘어남 |

**작업량:** 안 B 교체는 `pair_fit()` 안쪽 20줄. 30분이면 되고 되돌리기도 30분입니다. 위험은 낮습니다.

## 6. "이걸 잘 임베딩해주는 모델은 없나?" — 없습니다, 그리고 이유가 명확합니다

돌고 도는 게 아니라 **이번 바퀴에서 끝납니다.** 세 단계로 막힙니다.

### ① 임베딩할 게 없습니다

임베딩 모델은 **비정형 입력(텍스트·이미지)을 벡터로 바꾸는** 도구입니다. 우리 입력은 이미 벡터입니다 — 축 4개, 각각 0~1. 임베딩 모델을 붙일 자리가 없습니다. (§9에서 KURE를 붙여본 건 *케이스 문단*이라는 텍스트를 상대로였습니다.)

### ② "팀 궁합 임베딩 모델"은 존재하지 않습니다

그런 모델이 있으려면 **팀 구성 → 실제 성과** 라벨로 학습돼 있어야 합니다. 그런 공개 모델은 없습니다. 우리가 만들려면 팀 수백 개와 각 팀의 4주 뒤 성과가 필요한데, **우리 라벨 데이터는 0건**입니다. 3일 안에 못 모읍니다.

그리고 만약 그 데이터가 있다면 — **임베딩이 아니라 그냥 회귀나 분류를 하면 됩니다.** 임베딩은 목적이 아니라 중간 표현입니다.

### ③ 학습을 해도 집합 성질은 쌍 임베딩으로 안 담깁니다

§2의 반례가 여기서도 걸립니다. '몇 명이 주도하는가'를 담으려면 쌍이 아니라 **팀 전체를 하나의 벡터로 인코딩**해야 하고(DeepSets·Set Transformer 계열), 그건 다시 학습 데이터를 요구합니다. 학습 없이는 어떤 아키텍처도 우리 규칙을 알아낼 수 없습니다.

### 그래서 이게 결론이고, 발표 문장이 됩니다

> **"라벨 데이터가 0건인 상황에서는 학습 모델을 만들 수 없습니다. 그래서 문헌 근거를 규칙으로 옮겼고, 규칙이라서 왜 그 점수가 나왔는지 화면에 그대로 보입니다."**

**모델로 못 가는 게 약점이 아니라, 우리가 결정론을 택한 이유입니다.**

### 언제 학습으로 갈 수 있나 (승격 조건)

| 필요한 것 | 지금 |
|---|---|
| 팀 200개 이상의 구성 데이터 | 0건 |
| 각 팀의 4주 뒤 성과 라벨 | 0건 |
| 라벨의 신뢰도(누가 어떻게 매겼는가) | 정의 없음 |

**셋이 다 채워지기 전에는 규칙이 유일하게 가능한 방법입니다.** 이건 타협이 아니라 데이터 상태가 정한 결론입니다.

## 7. 정직한 갭

- 쌍 ρ은 **이진 입력 136쌍** 기준입니다. `confidence`를 켠 연속 입력에서는 다시 재야 합니다 `[미확인]`.
- 팀 ρ=0.812는 **검증 케이스 6개**만으로 낸 값입니다. n=6은 근거가 약합니다 — 15,504팀 전수로 다시 재면 정확해집니다(80초).
- §2의 반례 둘(전원 캡틴 vs 캡틴 0명 · 게이트 37건)은 **재현 가능한 사실**입니다. 표본이나 튜닝 문제가 아닙니다. 게이트 반례는 4,000팀 표본에서 찾았고, 전수(15,504팀)로는 더 많습니다.
- **초판 스크립트에 가중치 색인 버그가 있었습니다**(`WEIGHTS.values()`가 삽입 순서라 `AXES`와 어긋남). 팀이 직접 실행해서 잡혔습니다. **이 문서의 숫자를 쓰기 전에 `python cosine_variant.py`를 한 번 돌려 대조하세요.**
- 팀 환경(Windows·venv) 실행에서 §1·§5 세 값이 모두 `+1.000`으로 확인됐습니다.
